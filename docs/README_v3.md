# AI Operations Copilot

Backend service that helps an operations team answer customer and operational queries about orders and vehicles.

This document covers the interaction model, the entities, the assumptions behind them, how the data is modelled, and what the evals check.

---

## Position

The LLM is a query planner and a phrasing layer, not the reasoning engine.

The interesting queries in the brief aren't lookups. "Customer paid but delivery isn't scheduled, what's going on?" asks for a cause, and a cause generated by a model is unfalsifiable and unauditable. The cause is computed in code; the model phrases it.

```
NL query → router → deterministic execution → structured result → LLM phrases it → answer + evidence
```

Anything that can be wrong in a way that costs money is computed deterministically. The model only ever sees validated facts.

## How it's used

This is an internal console for the operations team. There is no customer-facing chat surface.

```
Customer (WhatsApp / call / email)
        │
        ▼
   Ticket created ────────────────┐
        │                         │ read-only evidence,
        ▼                         │ never a trigger
   Ops queue → Agent picks it up  │
        │                         │
        │ asks in own words       │
        ▼                         │
     COPILOT ◄────────────────────┘
        ▼
  Answer + evidence + rule_id + confidence (+ optional proposed action)
        ▼
  Agent reads and judges
     ├─→ replies to customer, resolves ticket
     └─→ approves a write action → idempotent execute → audit log
```

Two boundaries follow from this. **The ticket is data, not a trigger** — nothing a customer writes causes the copilot to act, which is the same boundary as the prompt-injection defence. And **the agent is the actor** — the copilot answers and proposes, the agent decides. That's what makes refusal cheap: the human is already there, so "no data supports this" costs one extra lookup rather than a lost customer.

### Autonomy tiers

| Tier | Who acts | Example | Status |
|---|---|---|---|
| 0 — Suggest | Agent, always | Diagnosis, summaries | Built |
| 1 — Draft | Agent approves the text | Copilot drafts, agent sends | Built |
| 2 — Auto-reply | System, read-only | "Your delivery is Thu 3pm" | Built, tightly gated |
| 3 — Auto-act | System, writes | Auto-refund a duplicate charge | Designed, not built |

Promotion between tiers is gated by **blast radius, not model accuracy**. Tier 2's worst case is a wrong date; Tier 3's is money leaving the company. Tier 2 auto-reply requires all of: shape is lookup, zero rules fired, one entity resolved unambiguously, read-only, and an allowlisted intent. Auto-resolved tickets queue for sampled review, and a customer reply reopens the ticket and force-assigns a human — auto-reply never gets a second attempt.

## Scope

The business runs two funnels. One is built.

| Funnel | Status |
|---|---|
| Buy-side (selling a car to a consumer) | Built end to end |
| Sell-side (buying a car from a consumer) | Two stub states only |

Sell-side is reduced to `SELLER_PAYOUT_PENDING` and `SELLER_PAYOUT_DONE` — enough to make cross-seam diagnoses work, where a buyer's delivery is blocked because the seller hasn't been paid, without building a second funnel.

Out of scope: financing and loans, insurance, test drives, inspection reports, hub and yard slots, transport legs, agent rosters, warranty, partner-dealer accounts. Each adds tables without adding a new class of failure to reason about. The tradeoff is depth over a narrow domain rather than thin coverage across all of it.

## Entities

Eleven entities plus an audit log — twelve tables. Enough to produce every failure mode under test, nothing beyond that.

| Entity | What it is | Key fields |
|---|---|---|
| `customer` | Buyer | id, name, phone, city_code, region |
| `vehicle` | The physical car | id, reg_no, make, model, year, km, listing_status |
| `order` | One transaction | id, customer_id, vehicle_id, state, city_code, region |
| `order_event` | Append-only state ledger | order_id, from_state, to_state, actor, reason, at |
| `payment` | Money in, or payout out | order_id, kind(token\|full\|payout), amount, status, txn_id, captured_at |
| `refund` | Money back | order_id, payment_id, amount, status, idempotency_key |
| `rc_case` | RTO ownership transfer | order_id, vehicle_id, status, blocked_reason |
| `refurb_job` | Reconditioning work | vehicle_id, status, blocked_reason, promised_at, completed_at |
| `delivery` | Handover | order_id, slot_at, status, attempt_count, courier_ref |
| `ticket` | The unit of work | see below |
| `ticket_message` | One message in the thread | ticket_id, direction, channel, author, body, injection_flagged, at |
| `action_audit` | Write trail | answer_id, proposal, proposed_by, approved_by, rule_id, idempotency_key, result |

Three properties of this model drive most of the design.

**`order_event` is the source of truth, not `order.state`.** The state column is a materialised convenience. When the two disagree that's a real defect, so it's a detectable one and instances of it are seeded.

**There are three units of reference and they don't line up.** An order is a transaction. A vehicle has a life across many orders: bought, refurbished, sold, returned, relisted. A ticket is the unit of work, and often arrives with no order number at all. So "what's the status" is ambiguous unless the intended one is known, and entity resolution is a feature rather than something bolted on later.

**`ticket.body` is untrusted.** It's written by people outside the company and lands in the model's context window. It's treated as an adversarial surface everywhere it appears.

### Ticket

```
ticket
  id, order_id?, customer_id, channel, subject, body,
  state, priority, assigned_to, city_code, region,
  created_at, first_response_at, resolved_at,
  resolution_code, resolved_by, resolution_evidence (jsonb)
```

```
OPEN → ASSIGNED → IN_PROGRESS ──┬─→ AWAITING_CUSTOMER ─┐
                                └─→ AWAITING_INTERNAL ──┤
                                                        ▼
                                                    RESOLVED → CLOSED
                                                        ↑  │
                                                        └──┴─ REOPENED
```

`order_id` is nullable on purpose — customers write "my Swift hasn't arrived" with no order number. `resolved_by` is an enum (`agent` | `copilot_auto`) and never blank; resolution without evidence is itself a detectable defect. Agent resolutions inherit the copilot's `rule_id` and evidence automatically, so every close is auditable.

## Authentication and scoping

**The copilot has no identity of its own. It is not a principal.** It executes as the calling agent under delegated authority and can never exceed what that agent could do by hand.

```
Agent authenticates → session issues { user_id, role, city_code, region, permitted_actions[] }
        ▼
SET LOCAL app.city_code / app.role   (inside the request transaction)
        ▼
Postgres RLS filters every row — not optional, not model-visible
        ▼
Action proposals filtered against permitted_actions, re-checked at execute
```

There is no service account. A copilot holding its own privileged credential is a privilege-escalation machine: every user gets the union of all permissions the moment they phrase a question cleverly. Scoping comes from the session, never from anything the model emits. Tier 2 auto-reply runs under `copilot_readonly`, a narrower context than any human.

### Why row scoping, given this is B2C

Cars24 sells to individual consumers, so there is no tenant in the SaaS sense — no customer organisation whose data must be walled off from another's. The isolation axis is operational:

- **Operational scope.** Ops is organised by city and hub. A Mumbai agent has no business reason to browse Delhi's tickets. This is data minimisation between employees, not a wall between customers.
- **PII exposure surface.** Every ticket carries a name, phone, address and a multi-lakh transaction. Scoped access bounds a compromised account to one city rather than the whole book.
- **Insider risk.** Used-car ops has real fraud vectors — collusion on valuations, leaking buyer details to competing dealers, refund abuse. Scoping plus the audit log makes these traceable.

| Role | Scope | Can |
|---|---|---|
| `l1_agent` | Own city | Read, ask, propose, resolve tickets, refund ≤ ₹25k |
| `supervisor` | Own region | Plus approve > ₹25k, policy exceptions, query console |
| `copilot_readonly` | Ticket in context | Lookup only, no writes |

Two human roles is the minimum that makes authorization testable. With one role every check passes and nothing is proven.

## Storage

Postgres 16 via `docker-compose`, with row-level security. The dataset is small enough for SQLite; the reason for Postgres is that the central claim of this design is *trust boundaries live in the data layer*, and RLS is what turns that from an assertion into something testable.

```sql
ALTER TABLE tickets ENABLE ROW LEVEL SECURITY;

CREATE POLICY city_scope ON tickets
  USING (
    city_code = current_setting('app.city_code')
    OR (current_setting('app.role') = 'supervisor'
        AND region = current_setting('app.region'))
  );
```

A forgotten filter now returns zero rows instead of everyone's rows — the failure mode inverts from silent leak to obvious break. It also means the supervisor query console needs no SQL rewriting: the connection itself cannot see out of scope, whatever is typed.

Notes: connect as a dedicated `app_user`, since RLS is bypassed by table owners and superusers and tests would otherwise pass for the wrong reason. Repository-layer predicates stay in place as defence in depth. The query console uses a `SELECT`-only role with a 5s statement timeout and a 500-row cap, and logs every query.

## Assumptions

**Domain**

1. One order maps to one vehicle. A vehicle can appear on many orders over time.
2. Payments capture asynchronously via webhook, so lag between capture and state advance is a real failure mode, not an edge case.
3. RC transfer gates dispatch. This appears to be the most common real stall, so it's modelled as the central one.
4. Refurb is scoped to the vehicle, not the order, so it can block a sale that's already been paid for.
5. Delivery gets three attempts before it needs a human.
6. Return window is 7 days from delivery confirmation, with an odometer-delta cap.
7. Thresholds (SLA hours, return window, odometer cap, refund limits) are configuration, never prompt text.

**Architecture**

8. The LLM is untrusted input. Not a security boundary, never a source of truth, never a principal.
9. Scoping is enforced by the database via RLS, not by instructing the model.
10. Retrieved text can never trigger a tool call. Tool calls come only from the operator's turn.
11. Writes are proposed, approved by a human, and idempotent. All three, always.
12. A dependency that's down gets named in the answer. It never silently becomes an empty result.
13. "No data supports an answer here" is a correct response and is tested for.
14. The fallback path must not be worse than the copilot.

**Simulation**

15. Seed data is deterministic with a fixed RNG seed, so evals are reproducible.
16. Volumes are illustrative (65 orders, 26 tickets), sized for testability rather than scale.

## Data model

### Order state machine

```
CREATED → TOKEN_PAID → FULL_PAID → REFURB_DONE → RC_DONE
        → DISPATCH_SCHEDULED → OUT_FOR_DELIVERY → DELIVERED
        → RETURN_WINDOW_OPEN → CLOSED
                            ↘ RETURN_REQUESTED → REFUNDED
```

Every state declares invariants, meaning what has to be true if things are healthy:

```
FULL_PAID ⟹ payment.status = captured
          ∧ refurb_job.completed
          ∧ rc_case.status = done within SLA(payment.captured_at)
```

### Diagnosis is a diff, not a narration

The engine computes expected state from the ledgers, compares it against what's actually there, and emits a structured violation:

```json
{
  "order_id": 1289,
  "expected_state": "DISPATCH_SCHEDULED",
  "observed_state": "FULL_PAID",
  "stuck_for": "62h",
  "primary_rule": "rc_transfer_stall",
  "blocking_entity": { "type": "rc_case", "id": "RC-8821", "reason": "seller_noc_missing" },
  "suggested_action": "escalate_rto"
}
```

The model phrases that. It can't invent a cause the data doesn't support because it never picks the cause.

### Rules

Each violated invariant is a named, versioned rule in code, not prompt text. Every answer carries the `rule_id`, the version, and the field values that fired it, so any answer can be replayed and a wrong one fixed in a single function.

| rule_id | Fires when | Blocking entity | Action |
|---|---|---|---|
| `payment_capture_lag` | Captured but state not advanced >30m | payment | replay_webhook |
| `rc_transfer_stall` | FULL_PAID >48h, RC not done | rc_case | escalate_rto |
| `refurb_overrun` | Refurb past promised_at | refurb_job | notify_customer_delay |
| `delivery_slot_missing` | RC_DONE >24h, no delivery row | — | schedule_delivery |
| `delivery_attempts_exhausted` | attempt_count ≥ 3 | delivery | call_customer |
| `refund_duplication` | >1 refund per payment_id | refund | freeze_and_review |
| `seller_payout_hold` | Linked sell-side payout stuck on KYC | payment | route_to_sellside |
| `inventory_double_allocation` | Vehicle on two live orders | vehicle | cancel_later_order |
| `return_window_boundary` | Return requested within ±24h of expiry | — | supervisor_exception |
| `state_ledger_mismatch` | order.state ≠ last order_event.to_state | order_event | reconcile |
| `ticket_first_response_breach` | OPEN past first-response SLA | ticket | assign_now |
| `ticket_resolved_without_cause` | RESOLVED with no rule_id or evidence | ticket | reopen_for_audit |
| `ticket_reopen_loop` | Reopened ≥2 times | ticket | escalate_supervisor |
| `ticket_orphaned` | No order_id, resolution attempted | ticket | request_identifier |
| `ticket_stale_blocked` | AWAITING_CUSTOMER >7d, no follow-up | ticket | auto_followup |

Because causes are structured IDs rather than sentences, they aggregate. That's what makes "what's the top reason deliveries slipped this month" answerable at all.

### Seed data

65 orders and 26 tickets.

| Bucket | Count | Purpose |
|---|---|---|
| Healthy | 40 | Background noise, otherwise aggregates are meaningless |
| Broken | 18 | At least one clean instance per rule, plus 3 where two rules fire at once |
| Unanswerable | 2 | Correct output is a refusal |
| Injection | 1 ticket | `ticket.body` carries a prompt-injection attempt |

Tickets span every state, including some with null `order_id`, some Tier-2 eligible, and some reopened twice. Three cities across two regions, two human users per city.

The seed script and the eval fixture are the same artifact from two directions. Every seeded defect exists so a labelled case can resolve against it.

## Evals

The fixture is `questions_v2.json`. Assertions are on the structured intermediate result rather than the prose, because prose isn't testable and `primary_rule` is.

**Metrics**

| Metric | What it means |
|---|---|
| Shape accuracy | Router picked the right execution path |
| Rule accuracy | Fired rules match expected, with `primary_rule` ranked first |
| Hallucination rate | Cases citing unsupported entities or violating `must_not_mention` |
| Refusal precision | Refuses when it should, doesn't when it shouldn't |
| Autonomy precision | Auto-reply fires only when every Tier 2 gate passes |
| Determinism | Paraphrases produce an identical structured IR |

**Coverage**

- The three example queries from the brief
- Terse, lowercase, malformed and paraphrased input
- Cases where two rules fire and the downstream symptom must not be reported as the cause
- Queries anchored on reg_no, or on a ticket with no order number
- Buy-side symptom with a sell-side cause
- Materialised state contradicting the event log
- Aggregates reaching SQL rather than retrieval
- Policy verdicts that expose the clock start and threshold instead of asserting from memory
- Write safety: no first-turn execution, role gate above the refund limit, idempotent replay, duplicate detection, bulk scope disclosure
- Ticket lifecycle: resolution provenance, closing without evidence, reopen loops
- Tier 2 autonomy: gate passes, gate blocked by a fired rule, gate blocked by shape, and no second attempt after reopen
- Adversarial: refusal on unmodelled claims, injection in ticket text, attempts to widen scope, a dependency that times out
- **RLS enforced at the database** — raw unrestricted SQL on a scoped connection returns zero foreign rows

## Query shapes

Everything routes into exactly one of these. Each has its own execution path and its own tests.

| Shape | Example | Path |
|---|---|---|
| Lookup | "Payment status for #4521?" · "Full status summary for #2231." | Typed fetch — one tool, or many fanned out and narrated |
| Diagnosis | "Paid for #1289 but no delivery, why?" | State diff + rules |
| Aggregate | "How many deliveries missed SLA last week?" | SQL |
| Cohort | "All orders stuck >21 days in RC transfer." | SQL + per-item rules |
| Policy | "Is #2231 eligible for a 7-day return?" | Policy evaluated as data |
| Action | "Issue the refund for #3310." | Proposal → confirm → idempotent execute |

Routing first, rather than one prompt handling all of them, is the central architectural decision.

There were seven shapes. `synthesis` — "give me a full status summary" — was folded into `lookup`, because the only thing separating them was how many tools ran in parallel. Breadth is a parameter of the plan, not a different kind of question, and a taxonomy that splits on breadth invites arguing about where the line sits. `aggregate` and `cohort` stay separate because reduce-to-a-number and retain-row-identity are genuinely different execution paths, and `policy` stays because its answer depends on configured thresholds the records do not contain — and because a policy question is usually hypothetical, describing something that has not happened, so no rule has fired and none will (DESIGN.md ADR-040). Aggregates in particular: routed through retrieval they produce confident wrong counts, which is worse than no answer.

**Seven again, for a different reason.** A `concept` shape was added later (DESIGN.md ADR-036) for questions about what a term *means* rather than what the records say — "what is the difference between token paid and full paid?". The six record shapes could not express it, so the system refused when asked plainly and improvised a definition when the phrasing dragged it into `diagnosis`. The second is the worse failure. `concept` answers from a curated glossary with no model call and no records read.

## API

```
POST /ask                      { query, ticket_id? } → answer + evidence + rule_ids + confidence
POST /actions/{id}/approve     idempotency key required
GET  /tickets                  RLS-scoped
GET  /tickets/{id}/records     entity graph for the fallback view
POST /tickets/{id}/resolve     resolution_code + evidence required
POST /tickets/{id}/reopen
POST /query                    supervisor only, read-only, capped
GET  /audit/{answer_id}        replay a past answer
```

`/ask` is the only natural-language surface. Everything else is typed. Session context is derived server-side and never accepted from the client.

## Console

Three-pane desktop layout: ticket context left, copilot conversation centre, evidence right.

The evidence pane has three depths. **Evidence** shows only the records the copilot cited, with the fired rule and the exact triggering field value. **Records** shows the full entity graph reachable from the ticket plus the order state timeline. **Query console** is read-only SQL, supervisor only.

Records is the fallback path. If the LLM provider is unavailable, an agent still has every record for that ticket laid out by entity — enough to work it by hand. Raw table browsing isn't offered to L1 agents, because an agent building their own joins produces confident wrong conclusions, which is exactly what the rules engine exists to prevent.

## Principles

1. The LLM is a query planner and a phrasing layer. Nothing else.
2. If it's expensive to get wrong, code computes it.
3. Every claim carries evidence. No evidence, no claim.
4. Refusal is a feature.
5. Writes are proposed, approved, and idempotent. All three.
6. Trust boundaries live in the database, never in the prompt.
7. The copilot is never a principal. It acts as the caller, never beyond them.
8. Autonomy is gated by blast radius, not by model accuracy.
9. The fallback path must not be worse than the copilot.
10. Go deep on a scoped domain and be clear about where the boundary is.
