# AI Operations Copilot

An internal console for a used-car marketplace's operations team. An agent opens
a customer ticket, asks a question in their own words, and gets back an answer,
the evidence behind it, and sometimes an action they can approve.

**The LLM is a query planner and a phrasing layer. Nothing else.**

```
NL query → router → deterministic execution → structured result → LLM phrases it → answer + evidence
```

The interesting questions are not lookups. "Customer paid but delivery isn't
scheduled, what's going on?" asks for a *cause*, and a cause generated by a model
is unfalsifiable and unauditable. So causes are computed in code by a versioned
rules engine, and the model phrases what the engine found.

Design rationale, diagrams and decisions: **[DESIGN.md](DESIGN.md)**.

## Running it

Requires Docker. Nothing else — no API key, no Python, no Node.

```bash
docker compose up --build
```

- Console → http://localhost:5173
- API → http://localhost:8000
- Interactive API docs → http://localhost:8000/docs
- Postgres → `localhost:5432`, database `copilot`

First boot takes a few minutes to build images and seed the database.

If a local Postgres already owns 5432:

```bash
POSTGRES_PORT=55432 docker compose up --build
```

Reset to a clean, identically-seeded database:

```bash
docker compose down -v && docker compose up
```

The seed is deterministic — no RNG anywhere — so a re-seed reproduces the exact
same dataset. That is what makes the eval suite repeatable.

### With no API key

This is the default, and it is a supported mode rather than a degraded one. The
stack boots on a **fake model adapter**: the console works, every endpoint
serves live rows from Postgres, and the full eval suite passes.

Verify:

```bash
curl -s localhost:8000/health
```

```json
{"ok": true,
 "model": {"adapter": "fake", "api_key_present": false, "redaction": "enforced"},
 "clock": {"now": "2026-09-10T12:00:00+05:30", "pinned": true}}
```

### With a live model

Copy the example env file and fill in a key:

```bash
cp .env.example .env
```

```bash
MODEL_ADAPTER=sarvam
SARVAM_API_KEY=your_key_here
```

```bash
docker compose up --build
```

`.env` is gitignored and is never baked into an image.

## Verifying the claims

### The eval suite — 58 cases

```bash
docker compose run --rm api python -m evals.run
```

```
58/58 passed
  action 9/9   aggregate 3/3   cohort 4/4   concept 1/1
  diagnosis 17/17   lookup 14/14   policy 3/3   query_console 2/2
  EVAL-7      all 15 rules covered
```

Cases assert on the **structured output** — query shape, the rule ids that
fired, the refusal flag, the entities cited — never on prose. Refusals and
prompt-injection attempts are graded cases, not absences.

Useful flags:

```bash
docker compose run --rm api python -m evals.run --shape diagnosis
docker compose run --rm api python -m evals.run --case L-01 --verbose
docker compose run --rm api python -m evals.run --live      # real provider
```

### Row-level security

```bash
docker exec copilot-db psql "postgres://app_user:app_user@localhost:5432/copilot" -tAc "
BEGIN;
SET LOCAL app.city_code='mum'; SET LOCAL app.role='l1_agent'; SET LOCAL app.region='west';
SELECT * FROM assert_rls_isolation();
COMMIT;"
```

```
ticket rows outside city scope|0|t
order rows outside city scope|0|t
ticket_message rows outside city scope|0|t
```

Also verifiable: a supervisor sees their region and not the next one; a
connection with **no** session variables set sees **zero** rows rather than all
of them; `UPDATE` on `action_audit` and `DELETE` on `order_event` are denied; and
`app_readonly` cannot write at all.

That third one is the property worth internalising. A forgotten filter returns
nothing instead of everyone's rows — the failure mode inverts from silent leak to
obvious break.

### Cross-city isolation, end to end

```bash
# Priya (Mumbai) can read her own ticket
curl -s -H 'X-Actor-Id: u_priya' localhost:8000/tickets/TKT-4830 | head -c 120

# Deven (Pune) gets 404 — not 403, which would confirm it exists
curl -s -o /dev/null -w '%{http_code}\n' -H 'X-Actor-Id: u_deven' localhost:8000/tickets/TKT-4830
```

## Who you are

There is no login. The actor comes from an `X-Actor-Id` header, defaulting to
`u_priya`. Authentication is stubbed; **authorisation is not** — scope and
permissions are read from the actor's row, so naming a different actor cannot
widen what you can see.

| Actor | Role | City | Refund limit |
|---|---|---|---|
| `u_priya` | L1 agent | Mumbai | ₹25,000 |
| `u_tariq` | L1 agent | Mumbai | ₹25,000 |
| `u_anil` | Supervisor | Mumbai | ₹1,00,00,000 |
| `u_deven` | L1 agent | Pune | ₹25,000 |
| `u_asha` | L1 agent | Pune | ₹25,000 |
| `u_ravi` | L1 agent | Bangalore | ₹25,000 |
| `u_nita` | Supervisor | Bangalore | ₹1,00,00,000 |

The role switcher in the console is a demo affordance only. In a real deployment
the session is derived server-side from the authenticated actor and is never
settable by the client.

## The console

| Screen | What it is |
|---|---|
| Queue | Tickets in scope, with SLA and assignment stats |
| Ticket workspace | Customer thread, details, copilot chat, evidence and trace |
| Console chat | Copilot without a ticket — questions about the whole book |
| Cohorts | Groups of orders sharing a fired rule |
| Query console | Supervisor-only SQL, read-only role, audited |
| Audit log | Every proposal, approval and execution |

Three behaviours are worth looking for, because they are the design arguing for
itself:

- **Refusal is a first-class answer.** Ask about something outside the seven
  query shapes and you get "I do not have an execution path for that question",
  with pointers — not a plausible guess.
- **Writes never execute on the turn they are proposed.** The approval modal
  shows the idempotency key and says so literally.
- **Resolve refuses** until you have asked something. A close with no `rule_id`
  and no evidence is a detectable defect, so the UI declines to create one.

### A demo path

Every step below was run against a clean clone; the quoted output is real.

1. Open **TKT-4821** ("Paid but no delivery date") → ask *"Why is this stuck?"*

   > RC ownership transfer has not completed, and dispatch is gated on it.
   >
   > Rule `rc_transfer_stall v2` fired on `order.state = FULL_PAID`,
   > `rc_case.status = blocked`, `hours_since_full_paid = 62`. The blocking
   > record is `rc_case RC-8821` (`seller_noc_missing`).

   A rule id, a version, and the row it fired on. Not a sentence about the data.

2. Follow up with *"And now?"* → resolves order 1289 again without being told.
   The entity came from the previous turn's stored IR, never from its prose.

3. Ask *"Draft a reply to the customer"* → a read that produces text. It never
   sends.

4. Open **TKT-4823** ("Refund not received") → ask *"Issue the refund for order
   #3310"*

   > More than one refund exists against the same payment.

   It proposes `freeze_and_review`, not a refund — the rules found a duplicate,
   so refunding again is the wrong action. As an L1 you cannot execute it;
   switch to `u_anil` to approve. Nothing happened on the turn it was proposed.

5. Open **TKT-4834** or **TKT-9001** (both carry injected instructions) and ask
   about the ticket → the instruction in the customer's message is reported,
   never obeyed.

6. In the **console chat** (no ticket), ask *"What is the weather in Mumbai
   tomorrow?"* → a refusal with a trace. Ask it again *after* a successful
   diagnosis in the same thread → still a refusal, because the sentence names a
   subject of its own and the thread is not an anchor for it. Then ask *"And
   now?"* → back to the last real question, because a refusal is not a question
   to repeat.

## API

Every endpoint resolves the caller from `X-Actor-Id` and runs inside one
RLS-scoped transaction. Out-of-scope records return **404**, never 403.

Interactive docs at http://localhost:8000/docs.

### Ask

| Method | Path | Body / params |
|---|---|---|
| `POST` | `/ask` | `{query, ticket_id?, conversation_id?}` |

The single entry point for every query shape. The request carries a conversation
**id**, never history — a client that could supply a transcript could fabricate
one, so turns are loaded server-side under the same scoped transaction.

```bash
curl -s -X POST localhost:8000/ask \
  -H 'content-type: application/json' \
  -H 'X-Actor-Id: u_priya' \
  -d '{"query":"Why is order #1289 stuck?"}'
```

```json
{
  "answer_id": "ans_b5f52caa",
  "ir": {"shape": "diagnosis",
         "entities": [{"type": "order", "id": 1289},
                      {"type": "rc_case", "id": "RC-8821"}],
         "confidence": 0.85},
  "verdict": "RC ownership transfer has not completed, and dispatch is gated on it.",
  "explanation": "Rule rc_transfer_stall v2 fired on order.state = FULL_PAID, rc_case.status = blocked, hours_since_full_paid = 62. The blocking record is rc_case RC-8821 (seller_noc_missing).",
  "evidence": [...],
  "trace": {...}
}
```

### Reads

| Method | Path | Returns |
|---|---|---|
| `GET` | `/health` | Liveness, active model adapter, whether the clock is pinned |
| `GET` | `/session` | The caller — role, city, region, permitted actions, refund limit |
| `GET` | `/tickets` | Queue in scope, with SLA and assignment stats |
| `GET` | `/tickets/{ticket_id}` | Ticket, customer, linked order, message thread |
| `GET` | `/tickets/{ticket_id}/records` | The evidence graph — every record behind the ticket |
| `GET` | `/cohorts` | Order cohorts grouped by fired rule |
| `GET` | `/cohorts/tickets` | The same for tickets |
| `GET` | `/audit` | Proposals, approvals and executions |

### Conversations

| Method | Path | Body / params |
|---|---|---|
| `GET` | `/conversations` | `?ticket_id=` or `?conversation_id=` |
| `GET` | `/conversations/list` | `?ticket_id=` — threads in scope, newest first |
| `POST` | `/conversations/new` | `{ticket_id?}` — closes the previous thread, never deletes |
| `DELETE` | `/conversations/{conversation_id}` | Ownership checked against the caller |

### Writes

| Method | Path | Body / params |
|---|---|---|
| `POST` | `/actions/{proposal_id}/approve` | `Idempotency-Key` header optional |
| `POST` | `/tickets/{ticket_id}/assign` | — |
| `POST` | `/tickets/{ticket_id}/resolve` | `{resolution_code, answer_id}` |
| `POST` | `/tickets/{ticket_id}/reopen` | — |

`/ask` never mutates. An action query writes a `pending_approval` row and returns
a proposal; approval is a separate call, where role and refund limit are
re-checked against the **approver**, not inherited from the proposal. Approving
an already-executed key records a no-op and changes nothing.

`/tickets/{id}/resolve` requires an `answer_id` — a resolution with no evidence
behind it is rejected.

### Query console

| Method | Path | Body |
|---|---|---|
| `GET` | `/query/schema` | — |
| `GET` | `/query/saved` | — |
| `POST` | `/query` | `{sql}` |

Supervisor only. Single `SELECT` statements, on a read-only role, 5s statement
timeout, 500-row cap, every query logged. No SQL rewriting is needed whatever is
typed — the connection itself cannot see out of scope.

## The database

Postgres 16 with row-level security. The dataset is small enough for SQLite; the
reason for Postgres is that the central claim of this design is *trust boundaries
live in the data layer*, and RLS is what turns that from an assertion into
something testable.

Three roles, and the split matters: `app_user` (application, RLS applies, owns
nothing), `app_readonly` (query console, SELECT only, 5s timeout), `app_migrator`
(migrations only). RLS is bypassed by table owners and superusers, so an
application connecting as either would make every isolation test pass for the
wrong reason.

### What is seeded

65 orders and 26 tickets across three cities and two regions: 42 healthy so
aggregates mean something, 21 broken with at least one clean instance per rule,
2 unanswerable where the correct output is a refusal, and several tickets
carrying prompt-injection attempts.

All 15 rules are seeded, and counts are asserted on boot — if `state_ledger_mismatch`
drifts from exactly 1, the ledger is wrong and that rule is measuring seed noise
rather than a real defect.

Each defect exists so a labelled eval case can resolve against it. The seed
script and the eval fixture are the same artifact from two directions.

## Tracing (optional)

Langfuse, self-hosted, and inert without keys — the stack runs identically with
or without it.

```bash
git clone https://github.com/langfuse/langfuse.git ../langfuse
cd ../langfuse && docker compose up -d      # UI on :3000
```

Create a project, paste its keys into `.env` as `LANGFUSE_PUBLIC_KEY` /
`LANGFUSE_SECRET_KEY`, and every stage boundary, prompt and model reply shows up
as a span.

**Self-hosted only.** A trace carries the operator's question and resolved entity
ids. Pointing `LANGFUSE_HOST` at a hosted instance sends those to a third party,
which is the boundary this design exists to hold. Only post-redaction prompt text
is ever captured.

## Principles

1. The LLM is a query planner and a phrasing layer. Nothing else.
2. If it's expensive to get wrong, code computes it.
3. Every claim carries evidence. No evidence, no claim.
4. Refusal is a feature.
5. Writes are proposed, approved, and idempotent. All three.
6. Trust boundaries live in the database, never in the prompt.
7. The copilot is never a principal. It acts as the caller, never beyond them.
8. Autonomy is gated by blast radius, not by model accuracy.
9. The fallback path must not be worse than the copilot.
10. Go deep on a scoped domain and be clear about where the boundary is.
