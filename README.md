# AI Operations Copilot

An internal console for a used-car marketplace's operations team. An agent picks
up a customer ticket, asks the copilot a question in their own words, and gets
back an answer with the evidence behind it — plus, sometimes, a proposed action
they can approve.

**The LLM is a query planner and a phrasing layer. Nothing else.**

```
NL query → router → deterministic execution → structured result → LLM phrases it → answer + evidence
```

The interesting questions here are not lookups. "Customer paid but delivery
isn't scheduled, what's going on?" asks for a *cause*, and a cause generated by
a model is unfalsifiable and unauditable. So the cause is computed in code by a
versioned rules engine, and the model phrases what the engine found. Anything
that can be wrong in a way that costs money is computed deterministically.

---

## Running it

```bash
docker compose up          # Postgres (seeded) + the UI
```

- UI → http://localhost:5173
- Postgres → `localhost:5432`, database `copilot`

If a local Postgres already owns 5432:

```bash
POSTGRES_PORT=55432 docker compose up
```

Reset to a clean, identically-seeded database:

```bash
docker compose down -v && docker compose up
```

The seed is deterministic — no RNG anywhere — so a re-seed reproduces the exact
same dataset. That is what makes the eval suite repeatable.

### The UI on its own

The frontend runs against fixtures and needs no backend at all:

```bash
cd ui && npm install && npm run dev
```

`VITE_API_MODE` is `mock` by default and `live` once an API exists. The two
implementations sit behind identical signatures in `ui/src/api/client.ts`, so
switching is an env var rather than a refactor.

## The database

Postgres 16 with row-level security. The dataset is small enough for SQLite;
the reason for Postgres is that the central claim of this design is *trust
boundaries live in the data layer*, and RLS is what turns that from an assertion
into something testable.

```sql
CREATE POLICY city_scope ON ticket
  USING (
    city_code = current_setting('app.city_code', true)
    OR (current_setting('app.role', true) = 'supervisor'
        AND region = current_setting('app.region', true))
  );
```

Three roles, and the split matters: `app_user` (application, RLS applies, owns
nothing), `app_readonly` (query console, SELECT only, 5s timeout), `app_migrator`
(migrations only). RLS is bypassed by table owners and superusers, so an
application connecting as either would make every isolation test pass for the
wrong reason.

### Verifying the claim

```bash
docker exec copilot-db psql "postgres://app_user:app_user@localhost:5432/copilot" -tAc "
BEGIN;
SET LOCAL app.city_code='mum'; SET LOCAL app.role='l1_agent'; SET LOCAL app.region='west';
SELECT * FROM assert_rls_isolation();
COMMIT;"
```

```
ticket rows outside city scope|0|t
order rows outside city scope|0|t
ticket_message rows outside city scope|0|t
```

Currently passing, alongside: a supervisor sees their region and not the next
one; a connection with no session variables set sees **zero** rows rather than
all of them; `UPDATE` on `action_audit` and `DELETE` on `order_event` are both
denied; and `app_readonly` cannot write at all.

That last one is the property worth internalising. A forgotten filter now
returns nothing instead of everyone's rows — the failure mode inverts from
silent leak to obvious break.

### What is seeded

60 orders across three cities and two regions: 40 healthy (so aggregates mean
something), 18 broken with at least one clean instance per rule and three firing
two rules at once, 2 unanswerable where the correct output is a refusal, and 1
ticket carrying a prompt-injection attempt.

All 15 rules are seeded. `SCOPE.md` §4 proposed trimming to 8; that was rejected,
because the trim left four eval cases permanently red and dropped both the only
cross-seam rule and the entire ticket-rule family.

Each defect exists so a labelled eval case can resolve against it. The seed
script and the eval fixture are the same artifact from two directions.

```
payment_capture_lag           1    seller_payout_hold              1
rc_transfer_stall             4    inventory_double_allocation     2
refurb_overrun                1    return_window_boundary          1
delivery_slot_missing         7    state_ledger_mismatch           1
delivery_attempts_exhausted   2    ticket_first_response_breach    3
refund_duplication            1    ticket_resolved_without_cause   1
ticket_reopen_loop            1    ticket_orphaned                 2
ticket_stale_blocked          2
```

`state_ledger_mismatch` must be exactly 1 — the seed asserts this on boot. If it
drifts, the ledger is wrong and that rule is measuring seed noise rather than a
real defect.

## The console

Five screens: queue, ticket workspace, records explorer, action approval, query
console. Every control does something and everything it does maps to a column in
the data model — see [docs/GLOSSARY.md](docs/GLOSSARY.md).

Three behaviours are worth looking for, because they are the design arguing for
itself:

- **Resolve refuses** until you have asked something. A close with no `rule_id`
  and no evidence is a detectable defect, so the UI declines to create one.
- **Refusal is a first-class answer.** Ask about a warranty commitment and you
  get "No data supports this", with pointers, not a plausible guess.
- **Writes never execute on the turn they are proposed.** The approval modal
  shows the idempotency key and says so literally.

The role switcher at the bottom right is a demo affordance only. In the real
system the session is derived server-side from the authenticated actor and is
never settable by the client.

## Principles

1. The LLM is a query planner and a phrasing layer. Nothing else.
2. If it's expensive to get wrong, code computes it.
3. Every claim carries evidence. No evidence, no claim.
4. Refusal is a feature.
5. Writes are proposed, approved, and idempotent. All three.
6. Trust boundaries live in the database, never in the prompt.
7. The copilot is never a principal. It acts as the caller, never beyond them.
8. Autonomy is gated by blast radius, not by model accuracy.
9. The fallback path must not be worse than the copilot.
10. Go deep on a scoped domain and be clear about where the boundary is.
